# 2) 추론 최적화
 
 추론 최적화는 **모델, 하드웨어, 서비스** 수준에서 할 수 있다.
 
 이상적으로는 속도와 비용을 위해 모델을 최적화해도 **모델 품질은 그대로여야 하지만,** 많은 최적화 기법이 모델 성능을 떨어뜨릴 수 있다.
 
 ![](https://velog.velcdn.com/images/algorithm_cell/post/51272b78-775f-443e-9ab8-39e51be7ac01/image.png)

- 서비스를 제공하는 업체마다 사용하는 최적화 기술이 달라 모델 성능이 다르게 나타나는 예시를 볼 수 있다.
 
 
## 모델 최적화
 
모델 자체를 수정하는 방식으로 효율성을 높이는 것을 목표로 한다. 
 
현재 많은 파운데이션 모델이 **트랜스포머 아키텍처를 따르고 자기회귀 언어 모델 구성 요소**를 포함하고 있다.

이런 모델들은 추론을 리소스 집약적으로 만드는 세가지 특징이 있다. **모델 크기, 자기회귀 디코딩, 어텐션 매커니즘이다.**

* *리소스 집약적* : 모델이 추론을 수행할 때 많은 계산 자원과 시스템 자원을 소모한다.

 
 
### 1. 모델 압축
 
**모델 크기를 줄이는 여러 기법**을 모델 압축이라고 한다.

앞선 챕터에서 **양자화와 증류**에서 자세히 다뤘다.

1. **양자화**
	a. 양자화는 모델의 정밀도를 낮춰서 메모리 사용량을 줄이고 처리량을 늘리는 것이다.
    
	- **가중치 전용 양자화 *weight-only quantization***는 가장 인기 있는 방법이다.
 
	- 쓰기 쉽고 많은 모델에서 바로 작동하며 효과가 뛰어나다.
    
2. **모델 증류**

	a. 작믄 모델이 큰 모델의 동작을 따라하도록 학습시키는 것이다.
    

3. **프루닝**
	
    a. 신경망 노드 전체를 제거하는 것으로, 아키텍처를 바꾸고 파라미터 개수를 줄인다.
    
    b. 예측에 도움이 되지 않는 파라미터를 찾아서 0으로 설정한다.

  	
    - 이렇게 하면 모델이 더 희소해져 모델 저장 공간도 줄고 연산도 빨라진다.
    - 하지만, 실제로 **잘 쓰이지 않는다.** 

      - 원본 모델 아키텍처에 대한 이해가 필요해서 진행하기 어렵다.

      - 다른 방법들에 비해 성능 향상 정도가 크지 않다.

      - 하드웨어 아키텍처가 희소성의 이점을 잘 활용하도록 설계되어 있지 않다.
      

### 2. 자기회귀 디코딩 병목 현상 극복하기

자기회귀 생성 과정을 조금만 개선해도 사용자 경험이 크게 향상될 수 있기 떄문에, 이 병목을 극복하는 새로운 기법들이 개발되고 있다.

1. **추측 디코딩**
	
    - 추측 샘플링이라고도 한다.
    
    - 더 빠르지만 성능이 낮은 모델(초안 모델)을 사용해서 토큰 시퀀스를 생성하고 목표 모델이 이를 검증하는 방식이다.
    
    ![](https://velog.velcdn.com/images/algorithm_cell/post/43e9523e-81c9-417f-beab-ec382e9b3640/image.png)
    
    - 초안 모델이 K개 토큰을 생성하고, 메인 모델이 동의하는 가장 **긴 연속 부분**을 수락한다.
    - **검증 과정은 병렬화할 수 있기 때문에, 검증하는데 걸리는 시간은 생성보다 짧다.**

2. **참조 기반 추론**

 - 모델을 사용해서 초안 토큰을 생성하는 대신 입력에서 초안 토큰을 가져온다.
 
 - **핵심**은 각 디코딩 단계에서 컨텍스트에서 가장 관령성 높은 텍스트 구간을 찾아내는 알고리즘을 개발하는 것이다.
 
 ![](https://velog.velcdn.com/images/algorithm_cell/post/d1c639cb-327d-4e9a-9823-cdfb37dd0cad/image.png)


3. **병렬 디코딩**

- 자기회귀 생성을 빠르게 하는 대신, 일부 기법들은 순차적 의존성을 없애는 것을 목표로 한다.

- 즉, **앞 토큰이 어떤 것인지 모르는 상태에서 뒷 토큰을 생성한다**

- 병렬 토큰 생성에는 **룩어헤드 디코딩 (같은 디코더 활용해 생성), 메두사 (다른 디코딩 헤드 활용)** 등이 있다.

- 이 과정은 **검증과 통합 과정이 반드시 필요하다**.

> 1. K개 미래 토큰이 병렬로 생성된다.
> 
> 2. 이 K개 토큰이 컨텍스트와 일관성이 있는지 검증한다.
>
> 3. 하나 이상의 토큰이 검증 실패하면, K개를 합치는 대신 실패한 토큰을 다시 만들거나 고친다.
>
> 이렇게 최종 출력에 통합될 때까지 모든 생성 토큰을 계속해서 정제하고 병렬 디코딩 알고리즘을 **야코비 디코딩**이라고 한다.

![](https://velog.velcdn.com/images/algorithm_cell/post/9be952e1-5e6b-4b39-854d-e02393530278/image.png)

### 3. 어텐션 메커니즘 최적화

1. **어텐션 메커니즘 재설계**

    - 어텐션 메커니즘이 작동하는 방식 자체를 변경한다.

    - 추론 최적화에 도움이 되긴 하지만, **모델의 아키텍처를 변경하기 때문에** **학습, 파인튜닝**단계에서만 적용할 수 있다.

      a. **로컬 윈도우 어텐션**

      - 새 토큰을 생성할 때 이전 모든 토큰에 어텐션을 적용하는 대신, ***인접한 고정된 크기의 윈도우 안에 있는 토큰에만 어텐션**을 적용한다. 

      - 유효 시퀀스가 **고정된 윈도우로 줄어들어서** KV캐시와 연산이 줄어든다.

      - 가까운 맥락을 잡아내는데 쓰인다.

      b. **크로스 레이어 어텐션**, **멀티 쿼리 어텐션**

        - 키-값 쌍 개수를 줄여서 KV캐시 메모리 사용량을 줄인다.

        - 크로스 레이어 어텐션 : 인접한 레이어들끼리 키, 값 벡터를 공유한다.

        - 멀티 쿼리 어텐션 : 헤드들끼리 키,값 벡터를 공우한다.

      c. **그룹 쿼리 어텐션**

      - 멀티 쿼리 어텐션을 발전시킨 방법으로, 쿼리 헤드들을 더 작은 그룹으로 나누고, **같은 그룹끼리 키,값 벡터를 공유한다**

      - 쿼리 헤드 수와 키, 값 쌍 수 사이를 유연하게 조절할 수 있다.


2. **KV 캐시 크기 최적화**

    >- 토큰 생성할 때 앞선 토큰의 키와 값 벡터를 다시 연산하는 대신, 이전 단계에서 연산한 **벡터들을 재사용한다.**
	  >
    >- 재사용을 위해 저장하는 캐시를 **KV 캐시라고 하고**, 이는 추론 시에만 사용된다.
	  >
    >![](https://velog.velcdn.com/images/algorithm_cell/post/766373c0-0136-4edd-8447-15c721adce57/image.png)
  	>	
    >- 토큰 하나 생성하려면 이전 모든 토큰과의 어텐션 점수를 계산해야하므로, 연산량이 **시퀀스 길이 제곱**에 비례해 증가하지만, KV캐시 크기는 **시퀀스 길이에 따라 선형적으로** 증가한다.
    >- KV 캐시 크기는 결국 사용 가능한 하드웨어 저장 공간에 의해 제한되므로 또 다른 병목 현상을 일으키므로 최적화가 필요하다.
	
    - vLLM은 **페이지드 어텐션**을 도입해서 KV 캐시를 연속적이지 않은 블록으로 나누어 메모리 단편화를 줄이고, 유연하게 공유해서 서빙 효율을 개선하고, 이를 통해 메모리 관리를 최정화한다.
    
    - 다른 기법으로는 KV 캐시 양자화, 적응형 KV캐시 압축, 선택적 KV캐시가 있다.

3. **어텐션 연산을 위한 커널 작성**

    - 어텐션 점수를 어떻게 연산하는지 설펴보고 이 연산을 더 효율적으로 만드는 방법을 찾는다.

    - 어텐션 연산에 최적화된 커널 중 하는 **플래시 어텐션**이다. 이 커널은 트랜스포머 기반 모델에서 많이 사용되는 여러 연산을 하나로 융합해서 더 빠르게 실행되도록 했다.

    ![](https://velog.velcdn.com/images/algorithm_cell/post/a1a91342-fa88-413b-97ea-86d99fbe9f90/image.png)
    
    > **커널**
    > - **GPU, TPU 같은 특정 하드웨어 가속기에 맞춰 최적화된 코드**이다.
	> - 연산량이 많고 반복적인 작업을 병렬로 실행해 하드웨어 성능을 최대한 끌어낸다.
    > - 행렬 곱셈, 어텐션, 합성곱 같은 핵심 AI 연산마다 전용 커널이 존재하며, 각 하드웨어에서 더 효율적으로 실행되도록 설계된다.
	> - 커널을 작성하려면 하드웨어 아키텍처에 대한 깊은 이해가 필요하고, 커널은 보통 CUDA, Triton, ROCm 같은 저수준 언어로 작성된다.
    
	
    > **커널의 연산속도를 높이는 방식**
    > 1. **벡터화**
    > 	- 루프(중첩 루프)에서 데이터를 하나씩 처리하는 대신, 메모리에서 연속으로 배치된 여러 데이터를 동시에 처리한다.
    >	- 이렇게하면 데이터 I/O	연산이 적어져 지연 시간이 줄어든다.
    > ``` python
    > # 벡터화 X한 경우
    > for i in range(8):
    >    C[i] = A[i] + B[i]
    > # 벡터화한 경우
    > C[0:8] = A[0:8] + B[0:8]
    > ```
    > 2. **병렬화**
    > 	- 입력 배열을 여러 코어나 스레드에서 동시에 처리할 수 있는 독립적인 덩어리로 나눠 연산 속도를 높인다.
    >
    ><br>
    >
    > 3. **루프 타일링**
    >	- 하드웨어 메모리 레이아웃과 캐시에 맞게 **루프의 데이터 접근 순서를 최적화한다.**
    >	- 하드웨어에 따라 달라지므로, CPU의 타일링 패턴은 GPU에 잘 맞지 않을 수 있다.
    >
    ><br>
    >
    > 4. **연산자 융합**
    >	- 여러 연산자를 단일 패스로 결합하여 불필요한 메모리 접근을 피한다.
  	>	- 모델의 연산자와 아키텍처를 더 깊이 이해해야한다.
    >
    ><br>
    >
    > - 커널은 **하드웨어 아키텍쳐에 최적화된다.**
    > - 따라서, 새로운 아키텍처가 나오면 새 커널을 다시 개발해야 한다.

  
      > **컴파일러**
      > - 로어링을 수행하는 도구로 ML 모델과 하드웨어 사이를 연결한다.
      > - 가능한 연산을 해당 하드웨어에서 빠르게 실행되는 전용 커널로 변환한다.
      >
      > **로어링**
      > - 하드웨어와 호환되는 언어로 **모델 스크립트를 변환하는 것**
      > 	- 모델 스크립트 : 모델 실행에 필요한 연산들의 순서와 구조를 정의한 것
      
      
      
## 추론 서비스 최적화
 
### 1. 배치 처리

- 운영 환경에서 각 요청을 하나씩 처리하는 대신, 비슷한 시간에 들어온 요청들을 묶어서 배치 처리하면 서비스 처리량을 크게 높일 수 있다.

1. **정적 배치 처리**

    - 정해진 수의 입력을 하나의 배치로 묶는다.

    - 따라서, 배치가 꽉 찰 때까지 모든 요청이 실행을 위해 기다려야 한다.

    ![](https://velog.velcdn.com/images/algorithm_cell/post/999ba30e-f389-478f-94e1-a73dd72f68ee/image.png)


2. **동적 배치 처리**

    - 각 배치에 최대 대기 시간을 설정해서, 정해진 개수의 요청 or 시간이 되면 처리한다.

    - 배치가 처리될 때 항상 꽉 차 있지는 않아서, 연산 자원 낭비로 이어질 수 있다.

    ![](https://velog.velcdn.com/images/algorithm_cell/post/b8508464-0bad-40fe-83e5-dd3e4ca6fcd5/image.jpeg)

- 기본적인 배치 처리 구현은 **배치 안의 요청이 모두 끝나야 응답을 반환할 수 있다.**

- 이로 인해 짧은 요청에 불필요한 지연이 발생할 수 있다.

3. **연속 배치 처리**
 
     - 연속 배치 처리는 배치의 응답들이 끝나는 대로 바로 사용자에게 반환될 수 있게 한다.

     - 한 응답을 만들 때 다른 응답을 막지 않는 연산들에 골라서 배치 처리하는 방식으로 작동한다

     - 배치가 실행 중(in-flight)인 상태에서도 요청이 들어오고 나가면서 계속 갱신된다고 해서 **인플라이트 배치 처리**라고도 한다.

	![](https://velog.velcdn.com/images/algorithm_cell/post/d104506d-6c26-4e01-80e8-5ba1a3f0f0b0/image.png)



 
### 2. 프리필과 디코딩 분리
 
 - 이 분리 방식은 **프리필 인스턴스에서 디코딩 인스턴스**로 중간 상태를 전송해야하지만, 고대역폭 연결을 갖춘 최신 GPU 클러스터에서는 통신 오버 헤드가 크지 않다.


- 프리필 인스턴스와 디코딩 인스턴스의 비율은 여러 요인에 따라 달라진다.

	
    - TTFT를 우선시한다면 2:1 ~ 4:1 
    
    - TPOT를 우선시한다면 1:1 ~ 1:2
 
 
### 3. 프롬프트 캐싱 (Prefix caching)

- 애플리케이션에서 여러 프롬프트에 **겹치는 텍스트가 있다.** 프롬프트 캐시는 이렇게 겹치는 부분을 재사용하기 위해 **저장해두므로, 한 번만 처리하면 된다.**

- 프롬프트 캐싱은 **긴 문서를 다루는 질의에도 유용하다.** 긴 문서를 캐시에 저장해 여러 질의에 걸쳐 재사용할 수 있다.

    ![](https://velog.velcdn.com/images/algorithm_cell/post/54acd6f8-8798-4e03-b18b-642476a3e4ec/image.png)




### 4. 병렬 처리

모델에 적용할 수 있는 병렬처리 전략은 **데이터 병렬 처리**와 **모델 병렬 처리**다.


1. **복제 병렬처리**

    - **서비스하려는 모델의 복제본을 여러 개 만들어 작업을 병렬화**하는 방식으로, 복제본이 많을수록 더 많은 요청을 동시에 처리할 수 있지만 더 많은 칩이 필요하다.

    - 학습 과정에서는 이와 동일한 기법을 **데이터 병렬처리**라고 한다.

2. **모델 병렬처리**

    - 종종 모델이 너무 커서 하나의 머신에 들어가지 않을 때, **하나의 모델을 여러 머신에 분산시키는 방식**을 의미한다.

    - 모델 분할 방법

        - **텐서 병렬 처리 (연산자 내 병렬 처리)**

            - 한 연산자에 포함된 텐서들을 여러 장치에 걸쳐 분할하여, 해당 연산자를 병렬로 실행할 수 조각으로 나눈다.

            - 지연 시간을 줄요주는 효과가 있다.

            ![](https://velog.velcdn.com/images/algorithm_cell/post/8cb23ca6-cdd3-48ae-9c03-339268245c55/image.png)
	
    	
        
        - **파이프라인 병렬 처리**
    
          - 모델의 연산을 여러 개의 독립적인 단계로 나눠 각 단계를 다른 장치에 할당하는 벙식이다.

          - 파이프라인 단계 간의 추가 통신 때문에 **총 지연 시간이 증가한다.**

          - 처리량을 높일 수 있기 떄문에 **학습 시에 사용된다.**
          
          ![](https://velog.velcdn.com/images/algorithm_cell/post/146a2a61-6c73-4218-bda6-0d40843a55bc/image.png)
      
   		



LLM에서 적용되는 전략 계열이다.

3. **컨텍스트 병렬처리**

    - **입력 시퀀스 자체가 여러 디바이스로 분할**되어 각기 따로 처리된다. 
    - ex) 입력의 전반부는 머신1, 후반부는 머신 2에서 처리할 수 있다.


4. **시퀀스 병렬처리**

    - 전체 입력에 필요한 **연산자들이 여러 머신**으로 분할된다
    - ex) 입력 처리에 어텐션과 피드포워드 연산이 필요하다면, 어텐션은 머신1, 피드포워드는 머신2에서 처리할 수 있다.

## 가드레일 도입하기

### 1. 입력 가드레일

- **외부 API로 개인정보가 유출되는 것**을 막아준다.
	
    - 완전히 막을 수 없지만, 줄일 수는 있다.
    
    - ex) 직원이 기밀이나 사용자 개인정보를 프롬프트에 복사해서 서드파트 API로 전송하는 경우
    
    - ex) 애플리케이션 개발자가 회사 내부 정책과 데이터를 시스템 프롬프트에 넣는 경우
    - ex) 도구가 내부 데이터베이스에서 개인정보를 가져와서 컨텍스트에 추가하는 경우
    
    ![](https://velog.velcdn.com/images/algorithm_cell/post/e6ebf3b4-7126-4ce6-ba0d-56a3ebb85eb0/image.png)


- **시스템을 망가뜨릴 수 있는 악성 프롬프트가 실행되는 것**을 막아준다.



### 2. 출력 가드레일

- 출력 가드레일은 **출력 실패를 탐지하고 다양한 실패 유형을 처리하는 정책을 명시한다.**
	
    - 품질
    
    	- 예상한 출력 형식을 따르지 않는 경우
       - 모델이 만들어 낸, 사실과 일치하지 않는 응답
      
        - 질이 매우 나쁜 응답
        
    - 보안
    	- 인종차별적이거나 성적인 콘텐츠, 불법적인 활동을 담은 유해한 응답
       
       - 개인정보나 민감한 정보가 들어있는 응답
       
        - 원격도구나 코드 실행을 유발하는 응답
        
        - 자사나 경쟁사에 대해 잘몰 설명해서 브랜드 위험을 초래하는 응답


- 실패는 재시도 로직으로 완화할 수 있지만, 지연시간과 비용을 늘릴 수 있다.

### 3. 가드레일 구현

- 가드레일에는 **신뢰성과 지연 시간의 트레이드 오프**가 따른다.

- 모델에 가드레일을 탑재할 때도, **안정성과 유연성의 트레이드오프**가 따른다.

- 모델 게이트웨이는 조직이 다양한 모델과 통합되고 **안전항 방식으로 상호작용할 수 있게 해주는 중간 계층이다.**

- **접근 제어와 비용 관리** 기능을 제공한다.
	
    - 사용자나 애플리케이션별로 어떤 모델에 접근할 수 있는지를 명확히 지정하는 세분화된 접근 제어가 가능하다.
    
    - API 호출 사용량을 모니터링하고 제한하여 남용을 방지하고, 비용을 효율적으로 관리할 수 있다.

- 모델 게이트웨이는 **속도 제한**이나 API 실패를 대비하기 위한 폴백 정책 구현에도 활용된다.
	
    - 주요 API를 사용할 수 없을 경우 대체 모델로 요청을 전달하거나 처리할 수 있다.
    
    - 이를 통해 애플리케이션이 중단 없이 안정적으로 동작하도록 보장한다.

- 게이트웨이는 구현이 비교적 간단해 즉시 활용 가능한 솔루션이 많다.
	
    - ex) Portkey, MLflow AI Gateway, Anyscale LLM Gateway, TrueFoundry, Kong, Cloudflare 등이 있다.


## 캐시로 지연 시간 줄이기

![](https://velog.velcdn.com/images/algorithm_cell/post/42bd8171-05d7-48b2-badf-f0ffdc3481c3/image.png)

### 1. 완전 일치 캐싱

- **정확히 같은 항목이 요청될 때만 캐시된 항목을 사용한다.**

	- ex) 벡터 검색이 중복되는 것을 피하기 위해 임베딩 기반 검색에서 사용한다.
    
- CoT처럼 여러 단계를 포함하거나, SQL 실행 등 시간이 오래 걸리는 동작이 포함된 질의에 특히 매력적이다.

- In Memory 저장소는 용량이 제한적이므로, PostgreSQL, Redis같은 데이터베이스나 계층형 저장소를 사용해 캐시를 구현할 수 있다.


- 캐시 크기를 관리하고 성능을 유지하려면 **제거 정책**이 중요하다.

	- LRU (least recently used)
    
    - LFU (least frequently used)
    
    - FIFO (first in first out)
    
    


### 2. 시맨틱 캐싱


- 들어온 질의와 캐시된 항목이 완전히 똑같지 않더라도 의미적으로만 비슷하면 캐시된 항목을 사용한다. 따라서 **두 질의가 유사한지 판단할 수 있는 방법이 확실히 있을 때만 제대로 작동**하기 때문에 **벡터 DB가 필요하다.**

- 벡터 검색이 포함되어 있어 시간과 연산량이 많다.

## AI 파이프라인 오케스트레이션

- 오케스트레이터는 **구성요소 정의, 체이닝** 두 단계로 작동한다.

### 1. 구성요소 정의

- 시스템이 어떤 구성 요소들을 쓰는지 오케스트레이터에 알려줘야 한다.

- 평가나 모니터링용 도구를 쓴다면 알려줘야한다.

- 다양한 모델, 검색을 위한 외부 데이터 소스, 시스템이 사용할 수 있는 도구들이 포함된다.

- 모델 게이트웨이를 사용하면 모델을 더 쉽게 추가할 수 있다.

### 2. 체이닝

- 기본적으로 함수를 조합하는 것으로, 여러 함수들을 하나로 엮는다.

- 체이닝에서는 **사용자 질의를 받는 순간부터 작업을 완료할 때까지 시스템이 수행하는 단계**들을 오케스트레이터에게 알려준다. 
 
- AI 오케스트레이션 도구는 **랭체인, LlamaIndex, Flowise, Langflow, Haystack** 등이 있다.

<br>

**오케스트레이터를 평가할 때 명심해야할 부분은 3가지 측면이다.**

### 1. 통합과 확장성

- 오케스트레이터가 **현재 사용 중이거나, 도입할 수 있는 구성 요소를 지원하는 지 평가해야한다.**

### 2. 복잡한 파이프라인 지원
	
- 애플리케이션이 복잡해질수록 여러 단계와 조건부 로직을 포함하는 복잡한 파이프라인을 관리해야할 수도 있기 때문에 지원하는지 확인해야한다.
    

### 3.사용 편의성, 성능, 확장성

-  직관적인 API, 포괄적인 문서, 커뮤니티 지원이 있어야 학습 부담을 줄일 수 있다.

# 2) 사용자 피드백

AI 애플리케이션에서 사용자 피드백은 **성능을 평가하고 개발 방향에 정보를 제공하는 것**뿐 이상의 의미를 지닌다.

**사용자 피드백은 독점데이터이고, 데이터는 경쟁 우위의 원천이다.**


## 피드백 종류

### 1. 명시적 피드백

- **사용자가 자신의 평가, 의도를 직접 표현한 데이터**이다.

- ex) 별점, 좋아요 / 싫어요 버튼, 리뷰, 평점 코멘트 등

- 의미가 명확하고 해석이 쉬우며, 사용자 의도가 직접적으로 드러난다.


### 2. 암시적 피드백

- 사용자 행동에서 추론한 정보이다.

- ex) 클릭 여부, 체류 시간, 구매/시청 기록, 검색 후 바로 이탈 여부

- 별도 입력 없이 자동 수집 가능하기 때문에, 데이터 양이 많고 연속적으로 쌓인다.

- 하지만, 사용자의 진짜 의도를 추론해야 하고, 노출/인기 편향이 발생하기 쉽다.


| 구분        | 명시적 피드백                          | 암시적 피드백                          |
| --------- | -------------------------------- | -------------------------------- |
| 정의        | 사용자가 **의도를 직접 표현**       | 사용자 **행동, 대화 패턴에서 간접 추론**|
| 해석 난이도    | 해석이 비교적 **쉬움**                   | 해석이 **어려움** (의미가 명확하지 않음)        |
| 사용자 노력    | **추가적인 행동 필요** (평점, 설문 등)        | **추가 노력 없음** (자연스러운 행동)          |
| 발생 빈도 | 사용자가 적거나 참여가 낮으면 **적게 발생**    | 운영 과정에서 **풍부하게 축적됨**             |
| 편향 문제     | **응답 편향** 존재 (불만족한 사용자가 더 많이 남김) | **노이즈와 해석 편향** 큼                 |
| 명확성   | 의미가 비교적 **직접적**                  | 동일 행동도 **긍·부정 해석이 모두 가능**        |
| 대표 예시     | 별점, 만족도 설문, 명시적 평가               | 대화 반복, 공유 행동, 질문 재시도             |
| 주의점  | 데이터 수가 적어 **전체 사용자 대표성 부족**      | 사용자별 행동 맥락을 **함께 고려해야 함**        |
| 활용 방식  | 개별 응답의 질 평가에 유리                  | **여러 신호를 결합**해 의도 추론             |
| 활용 전략  | 단독 사용 가능                         | **다중 신호 결합 시 효과적** (예: 공유 후 재질문) |


### 3. 대화형 피드백


### 3-1. 암시적 대화형 피드백
	
- 사용자 메시지의 내용과 의사소통 패턴을 통해 간접적으로 추론되는 피드백이다. 
  
  
![](https://velog.velcdn.com/images/algorithm_cell/post/6fc9255b-5c2e-40fb-843c-ce23572e61b7/image.png)


1. **자연어 피드백**

	- 사용자와 나눈 대화 내용에서 추출한 피드백을 의미한다.
 	
    - 성능을 모니터링하는데 유용하다.

2. **조기 종료**

	- 만약 사용자가 응답 생성을 멈추거나, 애플리케이션을 종료하거나 방치하는 경우를 의미한다.

3. **오류 교정**
	
    - 사용자가 후속 질의를 "아니요", "내 말은" 으로 시작한다면 모델의 응답이 빗나갔을 가능성이 있다.
   
    - 이렇게 다른 방식으로 표현하려는 시도는 **휴리스틱이나 ML모델을 통해 탐지할 수 있다.**
    
   ![](https://velog.velcdn.com/images/algorithm_cell/post/d6b4a65a-fa9c-454d-8475-afcc74c79610/image.png)


4. **불평**

	- 사용자들은 종종 애플리케이션의 출력을 교정하려고 하지 않고 불평만 하는 경우도 있다.


5. **감정**

	- 불평을 **부정적인 감정으로 표현할 수 있다.**




### 3-2. 기타 대화형 피드백

1. **재생성**
    - 사용자가 응답을 다시 생성했다면 첫 번재 응답이 만족스럽지 않았을 가능성이 크다.

    - 따라서 일부 모델은 재생성 이후 피드백을 요청하기도 한다.
        ![](https://velog.velcdn.com/images/algorithm_cell/post/a1c3786d-4bca-4c10-b299-cdcec8b4bb4e/image.png)

2. **대화 관리**

	- 삭제, 이름 변경 등 대화를 관리하기 위해 취하는 행동 또한 피드백이 될 수 있다.

3. **대화 길이**

    - 대화 당 턴수를 판단해 애플리케이션이 효율적인지 판단한다.

    - AI 친구 같은 경우 턴 수가 많을수록, 챗봇의 경우 턴 수가 적을수록 효율적이다.

    - 따라서, 애플리케이션에 따라 좋은 신호인지 나쁜 신호인지는 다르다.

4. **대화의 다양성**

    - 대화 길이는 토큰 수나 주제 개수로 측정할 수 있으며, 대화 다양성과 함께 해석되어야 한다.

    - 대화가 길더라도 같은 표현이나 짧은 문장만 반복된다면, 사용자는 루프에 빠졌을 가능성이 있다.


## 피드백 설계

### 1. 피드백을 수집하는 시점


1. **처음 시작할 때**

    - 사용자가 막 가입했을 때의 사용자 피드백은 동작 보정하는데 도움이 될 수 있다.

2. **문제가 생겼을 때**

    - 모델이 환각을 일으키거나, 정당한 요청을 처단하거나 응답이 너무 오래걸릴 때 **피드백을 남길 수 있어야한다.**

    - 이 과정에서 사람과 AI가 협력할 수 있고, 예시로 **인페이팅 기능이 있다.**

3. **모델의 신뢰도가 낮을 때**

    - 모델 자체가 특정 행동에 대해 확신하지 못할 때, 사용자에게 피드백을 요청해서 신뢰도를 높일 수 있다.
        ![](https://velog.velcdn.com/images/algorithm_cell/post/2315c18b-1de3-4b82-a9b6-cfd03982e5a1/image.png) ![](https://velog.velcdn.com/images/algorithm_cell/post/fc74ead6-777e-4d36-81a7-47726227a087/image.png)

        - 재미나이나 GPT는 비교 피드백을 위해 응답을 여러 개 제공하고, 사용자는 선호하는 방식을 선택해 피드백을 제공한다.

      ![](https://velog.velcdn.com/images/algorithm_cell/post/3dfe193f-8e2e-492f-8987-0504fa516896/image.png)

        - 구글 포토는 확신이 없을 때 사용자 피드백을 요청한다.


### 2. 피드백 수집 방법

- 피드백은 사용자의 워크플로우에 자연스럽게 녹아들어야 한다.

- 피드백 수집이 사용자 경험을 방해하지 않아야하며, 쉽게 무시할 수 있어야 한다. 추가적으로 인센티브도 있어야한다.


- 사용자 피드백을 공개할지 비공개할지 역시 중요하다.
	
    - 사용자들은 비공개 환경에서 더 솔직해지는 경향이 있다.
  
    - 하지만, **비공개 신호는 발견 가능성과 설명 가능성을 감소시킬 수 있다.**


## 피드백의 한계

### 1. 편향

1. **관대한 편향**

    - 실제보다 더 긍정적으로 평가하려는 경향을 말하고, 갈등을 피하고 싶거나 가장 쉬운 선택지일 때 발생한다.

    - 따라서 평점보다는, 글로된 선택지를 주는 것이 편향을 줄이는 방식이다.

2. **무작위성**

      - 악의가 아니라, 신중하게 생각할 동기가 부족해서 **아무렇게나 피드백을 주는 경우가 있다.**


3. **위치 편향**

	- 선택지가 사용자에게 어떤 위치로 제시되느냐가 그 선택지의 인식을 결정할 수 있다.
    - 일바적으로, 첫번째 제안을 클릭할 가능성이 높다.
    
    - 피드백 시스템을 설계할 때, **제안의 위치를 무작위로 바꾸는 등**의 방식을 사용할 수 있다.

4. **선호도 편향**

	- 최근성 편향 : 두 응답을 비교할 때 마지막에 본 응답을 선호한다.
    


### 2. 퇴화 피드백 루프

- **예측 자체가 피드백에 영향을 주고, 이 피드백이 다시 모델의 다음 비전에 영향을 주면서 초기 편향이 심해지는 현상**이다.

- 제품의 초점과 사용자층을 바꿀 수 있다. (*편향이 심해질 수 있다.*)

- 사용자 피드백으로 언어 모델을 학습 시에는 정확한 응답보다 **사용자가 선호하는 응답**을 하도록 만들어 **환각**을 심화시킬 수 있다.
